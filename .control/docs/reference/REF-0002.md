# Engineering conventions

## Overview

Non-negotiable standards for every line of Motioner code, documentation
and commit. They apply to humans and AI agents alike. When a rule must
be broken, the exception is documented in code and reviewed.

## 1. Language

- All source code, identifiers, comments, commit messages, tests, error
  messages, logs and project documentation are in English.
- The user may speak Spanish in chat; the agent replies in Spanish.
  Nothing inside the repository switches to Spanish.
- The PCS framework keeps some fixed Spanish section names and command
  names; those are upstream and are not application content.

## 2. Single source of truth and DRY

- One concept, one implementation. If logic is needed twice, extract a
  helper with a clear name and document its contract.
- Apply the rule of three: the second copy may still be local, the third
  copy must become a shared abstraction.
- No copy-pasted blocks between crates, tests or shaders. Share through a
  dedicated module, not through a utility dumping ground.
- Generated code is allowed only when a generator is committed and the
  output is reproducible.

## 3. Documentation

Every public API is documented with rustdoc: purpose, contract,
parameters, errors and panics. Every crate has a module-level overview
and a short README explaining its role and boundaries. Non-obvious
algorithms carry a short explanation of why, with a reference.

- Documentation explains intent and invariants, not restatements of the
  code.
- Examples in docs must compile as doctests when feasible.
- Architecture decisions go to `decisions/`, structure to
  `docs/reference/REF-0001`, standards to this file.
- When behavior changes, the documentation changes in the same commit.
- No dead documentation: remove or update stale text immediately.

## 4. Performance

- Optimization is budget-driven. Measure with benchmarks and profilers
  before and after a change.
- No per-frame heap allocation on hot paths; reuse buffers and arenas.
- Prefer data-oriented layouts for hot data; keep cold data separate.
- Avoid unnecessary clones, string formatting and dynamic dispatch in
  the render and evaluation loops.
- Every performance-sensitive change ships with a benchmark or a golden
  measurement.
- Correctness comes first; a faster wrong frame is still wrong.

## 5. Code quality

- `rustfmt` is mandatory; formatting is never discussed in review.
- `clippy` runs with warnings denied in CI. Lints that are disabled
  project-wide require a comment explaining why.
- No `unwrap` or `expect` in production paths except for proven
  invariants, with a message; user input never panics.
- `unsafe` requires a written justification and a safety comment; avoid
  it unless the engine boundary requires it.
- Core logic returns typed errors; `anyhow` is for application edges
  only.
- Functions do one thing. Files and modules have one responsibility.
  Split god modules before they grow; prefer many small helpers over one
  large function.
- No dead code, commented-out code or unused dependencies. CI checks for
  unused dependencies and warnings.
- No secrets, tokens or machine-specific paths in code, tests, logs or
  examples.

## 6. Helpers and reuse

- A helper must have a precise name, a documented contract and a single
  reason to change.
- Test helpers live in the testkit crate or a test support module, never
  copy-pasted across test files.
- Shader helpers live with shaders and use shared includes; do not
  duplicate math.
- Do not create vague utilities named `utils` or `helpers`; name the
  domain concept.

## 7. Errors, logging and observability

- User-facing messages are clear, actionable and English.
- Errors carry context and preserve the cause chain.
- Logs are structured, leveled and free of secrets and personal data.
- Panics are reserved for unrecoverable invariant violations and are
  reported with context.

## 8. Testing

- New behavior ships with tests; bug fixes ship with a regression test.
- Core logic uses unit and property tests; rendering uses golden frames;
  serialization uses round-trip tests; parsers use fuzz tests.
- Tests are deterministic and independent of execution order.
- Benchmarks live with the code they measure and run in CI for critical
  paths.

## 9. Git and review

- Commits are small, focused and use conventional commit messages in
  English.
- A change updates code, tests, docs and references together.
- The review checklist: no secrets, no dead code, errors handled,
  conventions followed, no out-of-scope changes, docs updated,
  performance measured when relevant, no duplication introduced.

## 10. Enforcement

- CI enforces formatting, clippy, tests, dependency boundaries, rustdoc
  warnings and unused dependencies.
- The code review skill in PCS is mandatory before commits.
- Exceptions are recorded in the PR or ADR, never silently.
