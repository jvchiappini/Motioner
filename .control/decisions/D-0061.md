## Contexto

E5 needs lattice, skinning and blend shapes on image() and video(), but both
node kinds only carry a destination box and a texture. Deformers only accept
path parts, so a generic engine mesh would have nowhere to receive its
positions. Adding media-specific deformers would duplicate the D-0059 and
D-0060 pipeline.

## Decision

An image or video owns an optional rectangular mesh: columns x rows vertices
with fixed UVs and fixed topology. The default is 2x2, which keeps the current
sprite quad and its byte-identical output. Mesh positions form an animatable
channel with the same fixed-topology rule as the E3 geometry channel: every
key must have the same vertex count, and a mismatch is the existing typed
topology error. The mesh works on standalone image/video nodes and does not
require a rig.

Inside a rig, an image or video can be declared as a part. Its mesh points are
the part's point set; paths and mesh vertices feed the same generalized
deformer implementations (lattice, skin, blend) with optional handles. The
media part runs the normal order: drivers, bone constraints, deformers and part
constraints. Texture key, UVs and fit stay media metadata, not deformer data.
A 2x2 mesh that is not deformed continues to use the existing sprite path so
all existing goldens stay byte-identical.

## Consecuencias

- One deformer implementation serves paths and media meshes.
- The engine receives a generic textured triangle mesh, not image-specific
  draw code.
- Mesh topology is an authored invariant; changing columns, rows or UV count
  is a structural edit, not a keyframe edit.
- Rig parts gain an optional media payload and mesh points, which expands
  PartBase/PartOutput and the DSL surface.
- The default 2x2 path must be proved byte-identical before the engine mesh is
  enabled for all media.
