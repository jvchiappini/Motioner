## Contexto

Phase 5 must play the deterministic stereo mix while the transport runs and
let the audio clock drive the playhead. `motioner_io` already owns ffmpeg
decode and the pure mixer; the preview needs one output device. The
workspace denies `unsafe_code` and the audio device is not render logic, so
it cannot live in `motioner_core`, `motioner_dsl`, `motioner_eval` or
`motioner_render`.

## Decision

Add `cpal` 0.15 (Apache-2.0) to `motioner_app` only. `motioner_app::audio_out`
opens the default output device, requests the device's default format, and
feeds it interleaved stereo frames from an `Arc<Mutex<Playback>>`; the UI asks
`ProjectHost::audio_position` for the playback cursor and seeks the transport
to that frame. The mixer stays in `motioner_io` and is shared by preview and
export.

Why writing it is worse: a correct WASAPI/CoreAudio/ALSA backend is
platform-specific and needs `unsafe`; `cpal` is the de-facto safe Rust
abstraction and is already used by most Rust audio tools.

Cost: `cpal` pulls `alsa`/`coreaudio`/`wasapi` bindings only for the host
platform (Windows here) and `dasp_sample`; the binary grows by roughly 1 MB.
Licence Apache-2.0, compatible with the outbound licence.

## Consecuencias

Gana: real device playback, an audio clock for the transport and no unsafe
code in Motioner. Export does not use the device at all.

Se pierde: a machine without an output device reports a typed error and the
editor keeps playing silently; the mixer and the timeline still work.
