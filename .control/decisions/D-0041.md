## Contexto

INITIATIVE-0014 plans an agent panel; D-0012 fixes providers, budgets and
human approval; D-0024 gives one typed command layer; D-0036 makes edits code
and records traces. This ADR fixes how the in-app agent works, so that any
provider (Anthropic, OpenRouter, Google, the Motioner model) behaves the same
and so that every session is valid training data (D-0040).

## Decision

### 1. Harness

- An agent panel docked in the editor: conversation, attachments (assets,
  frames, selection), inline renders, a change review (diff per turn,
  accept/reject, undo grouping) and budget/cost display.
- A provider abstraction with streaming, tool calls and image input:
  Anthropic, OpenRouter, Google (user keys in the Windows Credential Manager,
  D-0012), the **Motioner API** and the **local Motioner model**. Providers
  without image input use the text tools of §4.
- A context builder: a short system prompt per provider (long for general
  models with MDF docs, `std` reference and design rules; short for the
  Motioner model, which already knows them), the project summary, the
  selection and the current frame. Details are fetched by tools, never dumped.
- The tool list is generated from `motioner tools --schema` (D-0036): the
  D-0024 commands plus code, vision, design and asset tools. No private path:
  if the agent needs something, it becomes a tool everyone can use.
- Safety: no shell, no network beyond the provider, file access only inside
  the project through tools, confirmation for destructive or expensive actions
  (delete, long renders), final export always approved by the user (D-0012).

### 2. Workflow

The system prompt and the training data (D-0040) enforce one sequence:

1. **Understand** the request, the project and what is selected.
2. **Find gaps**: what is missing, what can be assumed safely.
3. **Decide** to ask or to assume (§3).
4. **Design plan**: style, palette, type, tempo and beat-by-beat scenes, each
   with a reason; shown to the user as a short storyboard.
5. **Build** through tools (code edits or commands; all write-through).
6. **Verify**: render key frames and a filmstrip, look at them, run
   `check_design`, fix the worst problem first; repeat within budget
   (D-0012 defaults: 10 iterations, 10 minutes, cost cap).
7. **Report**: what was made, what was assumed, what to try next.

### 3. Clarifying questions

- Ask only when the answer changes the result a lot and no good default
  exists: exact text, brand or logo, platform/aspect, contradictory tone,
  missing assets the user mentioned.
- At most three questions per turn, each with options and one recommended
  default (rendered as a picker, like a multiple-choice dialog), plus free
  text.
- **Visual questions** for style: the agent renders 2–4 small style
  thumbnails (theme, type, motion feel) and asks the user to pick; the choice
  is a preference signal (D-0042).
- When the agent does not ask, it states its assumptions in one line and
  proceeds; the user can correct them later.

### 4. Vision

- The agent can see: rendered stills, filmstrips (N frames in a strip),
  contact sheets, a short clip as sampled frames, imported images and video
  frames, and the editor viewport.
- **Set-of-marks overlays**: images can be rendered with numbered boxes and
  ids for every node (or a subset), so the agent can refer to "#7" and map it
  to a node and to its code statement.
- Every visual tool has a text twin (`describe_frame`, `check_design`,
  `layout_report`) built from the scene graph, so text-only providers and the
  small model can verify exactly, and vision is used for taste and for user
  media.

### 5. Traces

Every session is recorded in the D-0036 trace format with conversation, tool
calls, images (by reference), the user's decisions and the final state, under
the consent rules of D-0042.

### 6. The Motioner API

The Motioner model is offered as a provider of this same harness (and as an
HTTP API for external agents) with the same tool schema. Its advantage is
built-in knowledge of MDF, `std` and the rubric, so it needs a much smaller
context and is faster and cheaper. The API reports the MDF/`std` version the
model was trained on; the harness sends the project's version.

## Consecuencias

Gana:
- One harness and one tool schema for every provider, the local model and
  external agents; every session is useful data.
- Exact verification through scene-graph tools, with vision on top for taste.
- Ambiguous requests get targeted, visual questions instead of guesses.

Se pierde:
- Vision costs tokens; filmstrips and overlays must be small and cached.
- Several providers plus our own model to test.

*Amended 2026-11-03 (user decision):* **no simulated providers.** The
harness ships with real providers only; Anthropic is the first one and the
user tests it with their own key. Unit tests cover what does not need the
network (request building, SSE parsing from real captured payloads, tool
execution, context building, budgets). End-to-end tests call the real API
and run only when a key is available (ignored otherwise, never faked).

Pendiente:

- Panel UI design and the change review.
- Provider routing and fallback.
