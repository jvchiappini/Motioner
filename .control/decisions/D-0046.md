## Contexto

Phase 2 needs a native "choose folder" dialog for New project and Open
project. The workspace denies `unsafe_code` (`Cargo.toml` -> `[workspace.lints]`),
so calling `IFileOpenDialog` through the `windows` crate directly would need an
unsafe wrapper that is not worth owning. The dialog is UI chrome, not document
or render logic.

## Decision

Add `rfd` 0.15 (MIT) to `motioner_app` only, feature `xdg-portal` disabled on
Windows; the application implements
`motioner_ui::FolderPicker` over `rfd::FileDialog`, and the window asks the
trait. `motioner_ui`, `motioner_core`, `motioner_dsl`, `motioner_eval`,
`motioner_io` and `motioner_render` never see the crate.

Why writing it is worse: a correct COM modal dialog is ~300 lines of unsafe
Win32 plus shell interop that must own an apartment-threaded COM scope, while
`rfd` already ships the tested implementation and falls back to a native
folder dialog on Windows 10+.

Cost: `rfd` 0.15 pulls `windows-sys` (already in the graph through `winit`),
`raw-window-handle`, `pollster`, `ashpd`/`zbus` on Linux (not built on the
reference Windows machine) and `objc2` on macOS (not built). Windows build
adds roughly 1.5 s of compile time and no runtime state. Licence is MIT, which
is compatible with Apache-2.0 outbound and is recorded in `NOTICE`.

## Consecuencias

Gana: a native picker with no unsafe code in Motioner, the dialog isolated in
the application crate, and headless tests that never open a window.

Se pierde: one more dependency tree to audit on a platform bump; on a machine
without a desktop session the dialog returns `None`, which the UI reports as a
typed "cancelled" state instead of panicking.

Pendiente: file-association registration waits for the installer
(INITIATIVE-0021), and drag-and-drop stays in the engine feature (see the
file-drop commit in the FerrousEngine clone).
