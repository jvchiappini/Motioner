## Contexto

Parts are independent symbol nodes with transform offsets produced by
drivers. The mascot needs pupils that follow a look vector and hair/sparks
that follow or lag, and prompt 16 also asks for IK, path following,
copy/limit and distance constraints. Applying these in separate passes would
make the order ambiguous and duplicate state between bake and runtime.

## Decision

Add one ordered `motioner_rig::constraint` stage after deformers. Every
constraint reads `PartOutput`, the part bases and the frame's property
values, and mutates only part transforms.

- `Aim`: existing pupils offset by `look * radius`; the legacy `Rig::aims`
  list is converted into this variant at the start of a bake, so aim shares
  the stage.
- `TwoBoneIk`: root and middle part with a Vec2 target, optional Vec2 pole,
  and a tip length. It solves the elbow with the law of cosines, clamps the
  reach, picks the pole side, and writes the upper rotation plus lower
  position/rotation offsets.
- `FollowPath`: samples the target part's geometry by flattening it and
  walking arc length to the progress property; optionally orients the part
  along the tangent.
- `Copy`: copies position, rotation and/or scale offsets from another part.
- `Limit`: clamps position offsets and rotation offsets.
- `Distance`: keeps a fixed distance from another part along the current
  direction.
- `Spring`: a deterministic per-frame semi-implicit spring towards a Vec2
  property. Velocity/position state lives in `SpringState`, one entry per
  spring, and is replayed from frame zero. Stiffness, damping and mass are
  validated; non-finite targets are typed errors.

The stage runs after every deformer, in declaration order, and before the
bake writes keys. `bake` allocates the spring state once per bake so repeated
frames update it deterministically; `evaluate` is still a replay from zero.

## Consecuencias

- Evaluation order is now explicit and tested: properties -> machine ->
  drivers -> deformers -> constraints -> draw/bake.
- Spring is stateful by nature but deterministic: two bakes from frame zero
  are equal, and backwards seeking replays. A future runtime must carry the
  same state.
- IK is a two-bone constraint on part joints, not a general bone solver;
  skinning remains the deform stage. The model is enough for the prompt's
  acceptance and does not introduce a second skeleton.
- Constraint targets and gains are ordinary properties, so property
  write-through edits them; the structural constraints are source
  declarations.
- Textured mesh and engine work stay out of this stage (E5).

## Addendum (E5 reviewer finding)

Bone constraints run on the rig's bone poses before skinning. `BoneConstraint`
has `Aim`, `TwoBoneIk`, `Copy` and `Limit`, targeting `m.bone` joints. The
pipeline becomes properties -> machine -> drivers -> bone constraints ->
lattice/skin/blend -> part constraints -> draw. `m.ik`, `m.copy`, `m.limit`
and `m.aim` select the bone path with a `bone:` prefix; mixing a part and a
bone in one constraint is a typed error. `Rig::bone_constraints` is separate
from part constraints only so the order is explicit; there is still one
constraint implementation and one skeleton.

Skin stores indices into Rig::bones, never a cloned hierarchy. Bind pose
and parent resolution are read from the live rig, so a bone declared after
m.skin cannot leave a stale second skeleton. The skin's index list remains
the set of bones it was authored with; later bones do not silently join an
existing skin.
