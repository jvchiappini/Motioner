## Contexto

The goal (D-0036) is a small model, runnable locally, that produces beautiful,
fluid motion design in MDF, reasons step by step, asks when a brief is too
ambiguous, and understands what it sees in rendered frames and user media.
A small model reaches that only with data that is consistent, high quality and
**verified automatically**. Motioner owns a deterministic renderer and the full
scene graph of every frame, so it can score every example and label every
image exactly. This ADR fixes what the data looks like and how it is judged.

## Decision

### 1. Model family

- A small open-weights **vision-language** model as the base (text + image
  input, code output), fine-tuned in two sizes: a local tier (about 2–4B,
  4-bit, must fit the reference RTX 4050 with 6 GB next to the editor) and a
  cloud tier (about 7–14B) for the Motioner API (D-0041).
- The exact base model is chosen by a benchmark on the D-0040 eval set, and
  only among licences that allow commercial fine-tuning and redistribution.

### 2. Example format

Every generation example is one conversation in the harness format (D-0041):

1. System context (short for our model) and the project state summary.
2. User brief (Spanish or English, informal or precise).
3. Optional clarification turn: the assistant's questions with options and a
   recommended default, then the user's answers.
4. **Reasoning**, structured and short: understanding, gaps and assumptions,
   design rationale (style, palette, type, tempo and why), beat-by-beat plan.
5. Tool calls and their results (including renders and `check_design`), with
   short critiques and fixes.
6. Final program, `motioner fmt` clean, with the plan as comments mapped to
   `scene` blocks (D-0039).

The reasoning is part of the training target; it is kept only when the final
result scores high (§5), so the model learns reasoning that produces good
videos, not reasoning that only sounds good.

### 3. Task mix (initial, tuned by evaluation)

| Task | Share |
|---|---|
| Brief → (questions) → reasoning → program | 35% |
| Program + instruction → edit (code diff) | 25% |
| Vision: grounding, critique and media understanding (§6) | 15% |
| Agent trajectories with tool calls and self-correction | 10% |
| Clarification decisions (ask / do not ask) | 5% |
| Program → description | 5% |
| Repair (broken program + error → fix) | 5% |

Edit data is generated in reverse as well: apply a known transformation to a
good program (slower, other palette, no stagger, 9:16) and have the teacher
write the instruction that would ask for it.

### 4. Diversity

Briefs are produced by a seeded generator over a taxonomy: type (kinetic
typography, logo reveal, data viz, explainer, lower thirds, social vertical,
UI mockup, loop, transition, intro/outro), style (minimal, glass, brutalist,
retro, corporate, playful, editorial, neon), duration (3–30 s), aspect (16:9,
9:16, 1:1), energy, density, palette and language of on-screen text.
Duplicates are removed by AST similarity and by visual similarity of contact
sheets; no taxonomy cell may exceed its quota. At least 20% of programs are
built without presets, so the model also learns hand-made motion.

### 5. Quality rubric (the filter and the reward)

Each candidate is rendered headlessly and scored; candidates are generated
N times per brief and only the best that pass every gate is kept.

- **Validity (gate):** compiles, no warnings, no overrides, deterministic,
  no blank frames, `fmt --check` and `lint` clean.
- **Fluidity (from the curves, exact):** no velocity discontinuity at keys
  unless the ease is `hold`; peak speed in px/frame within bounds per element
  size; linear eases only where allowed (rotation loops, tickers); onsets are
  staggered (not everything starts on one frame); no dead time above a limit
  and no overload (too many large movers at once); motion blur on fast moves
  when the brief allows it.
- **Layout (from the evaluated scene):** text inside title safe, no unwanted
  overlap of text with text or with busy shapes, WCAG AA contrast for text
  against what is actually behind it, alignment to a grid, a clear type
  hierarchy.
- **Legibility:** each text stays readable for at least 0.5 s + 0.3 s per
  word; entrances do not overlap reading of the previous line.
- **Taste:** a visual judge (frontier model) scores a contact sheet and a
  short clip with a fixed rubric; the judge is calibrated against 100–200
  videos scored by the project owner, whose judgement is the reference.

The same metrics are exposed to agents as `check_design` (D-0041) and used as
the reward for reinforcement learning (§8).

### 6. Vision data

The renderer knows every node's box, colour, text, z-order and motion, so
vision labels are exact and free:

- **Grounding:** "where is the title?" → box; "which element is at (x, y)?" →
  node id; set-of-marks images with numbered boxes for referring.
- **Reading:** text content, font size class, colours, palette extraction.
- **Motion:** filmstrips or frame pairs → which element moves, direction,
  approximate ease family, what enters/exits, stagger order.
- **Defects:** the same frame with injected problems (overlap, off-screen,
  low contrast, clipped text, jitter, unreadable hold, misaligned row) →
  detect, localise and name the fix.
- **Comparison:** two renders of the same brief → which is better and why
  (from the rubric scores), for preference training.
- **Frame ↔ code:** an element in the frame → the statement that made it.
- **User media:** describe an imported image or video frame, find empty space
  for text, dominant colours, salient subject; labels from licensed datasets
  or the teacher, never from user data without consent (D-0042).

### 7. Teacher and legal gate

- The base corpus is generated by a frontier model (Claude Fable 5 is the
  candidate) with tools and rendering in the loop.
- **Before any generation at scale**, the terms of the chosen provider are
  reviewed for training a model that will be sold. If they do not allow it,
  the teacher changes (a provider or open model whose terms allow it). Human
  signals from Motioner users (D-0042) are the second source and do not
  depend on any provider's terms.
- Only OFL fonts and generated or permissively licensed media appear in the
  corpus (D-0013).

### 8. Training stages

1. Supervised fine-tuning on the filtered corpus (order of 50–150k examples,
   programs under 4k tokens).
2. Preference optimisation with renderer-scored pairs.
3. Reinforcement learning with verifiable rewards: the rubric of §5 plus
   clarification reward from a simulated user that holds a hidden full brief
   (reward = final quality − a small cost per question).

### 9. Evaluation and release targets

A fixed, never-trained set of about 300 briefs (plus vision and edit suites).
A model version ships only if it meets or beats the previous version on every
metric and reaches:

- compile rate ≥ 99%;
- clarification: asks when key information is missing in ≥ 90% of cases,
  asks unnecessarily in ≤ 10%;
- zero severe fluidity violations;
- judge preference vs the teacher ≥ 50% on in-domain briefs;
- vision grounding accuracy and defect recall reported per category;
- blind review by the project owner.

## Consecuencias

Gana:
- Every example is verified; the renderer is a free, exact labeller and
  reward.
- One format serves generation, editing, vision and agent behaviour.
- Measurable targets replace "perfect".

Se pierde:
- Large compute for rendering candidates and running the judge.
- The rubric encodes taste; a bad rule trains bad habits, so rules change only
  with evidence from evaluation.

Pendiente:
- Where the training pipeline lives (separate repository) and its compute.
- Teacher selection after the legal review.
- Base model benchmark.
