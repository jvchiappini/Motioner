## Contexto

Spec §9 promises that every created node gets a provenance path and that UI
edits become overrides stored next to the program, but §17 deferred the
syntax, orphan reporting and bake to v0.1. D-0011 makes the MDF program the
truth and the document a compiled artifact; until now the editor was
read-only because there was no place to put an edit.

`motioner_core` had no node identity beyond the creation index (`NodeId`),
no visibility flag and no content setters; `motioner_dsl` recorded no
provenance and its `Diagnostic` had no severity, so an orphan could only be a
hard error; `motioner_ui` had no edit model, no undo and no overrides file to
write to.

## Decision

### Identity

Every node carries a `NodeIdentity`:

- An explicit identity from `.id("name")` wins. Names are unique per
  document and match `[A-Za-z_][A-Za-z0-9_.-]*`; a duplicate is
  `CoreError::DuplicateId` in the core and a diagnostic at the `.id()` call
  in the DSL.
- Otherwise the identity is a **provenance key** built from the byte offset of
  the creating call's source span start, the call-site offsets of the user
  function frames on the stack (innermost first) and the iteration index of
  every enclosing `for` loop, rendered as stable text:
  `@<span start>/c<call start>.../i<index>...`. For example `@412/i3` is the
  node created by the call starting at byte 412 inside the fourth iteration of
  the innermost loop; `@88/c301` is a node created at byte 88 by a function
  called from byte 301.

Stability is honest, not absolute: the same program text always yields the
same keys (the interpreter is deterministic and hash maps are never
iterated), but **editing any line above a call shifts its byte offsets** and
therefore its key. Nodes users intend to edit should carry `.id("...")`. The
editor offers "Assign ID" in the inspector so users can adopt an explicit
name, and shows the current key with a copy action.

### Overrides file

`<name>.overrides.motion` sits next to `<name>.motion` (the project folder of
spec §15 does not exist yet). It contains only:

```text
override("id", "property", value)
override_key("id", "property", time, value, ease="linear")
override_unkey("id", "property", time)
override_visible("id", false)
override_locked("id", true)
```

Times are seconds like `key()`, converted with the composition rate. `value`
uses the same shapes as the property: `(x, y)` tuples for position, scale and
anchor, numbers for rotation and opacity, strings for `fill`, `stroke`,
`color`, `text`, `align` and `name`. The editor writes the file in a canonical,
deterministic order — first the header comment, then entries sorted by id,
property and time — one statement per line with no blocks, so the file is
trivially diffable.

### Overridable properties

- Transform: `pos`, `scale`, `rotation`, `anchor`, `opacity`, including their
  keyframes. Vector properties (`pos`, `scale`, `anchor`) have **independent
  per-axis channels**: `pos.x`, `pos.y`, `scale.x`, `scale.y`, `anchor.x`,
  `anchor.y` can be keyed, retimed, eased and removed separately, and the
  editor shows one timeline row and one stopwatch per axis. `key("pos", ...)`
  still keys both axes at once (2D); a future 3D transform extends the axis
  list with `z`.
- Content: `width`, `height`, `radius`, `fill`, `stroke`, `stroke_width`
  (rect/circle); `text`, `size`, `color`, `align` (text).
- Editor state: `visible` (rendered or not) and `locked` (editor only, no
  render effect).
- `name` is the display name shown in the layers panel; it never changes the
  node's identity.

### Orphans

An override whose id matches no node, or whose property does not apply to the
node's kind, is kept in the file and reported as a **warning** diagnostic.
Nothing is ever dropped silently.

### Bake

`motioner bake <file.motion> [--id ID]...` rewrites overrides into the program
for nodes whose identity is reachable from a top-level variable binding at the
end of the program (`title = text(...)` is the common case). It appends one
generated block introduced by
`# --- baked by motioner (do not edit above this line by hand) ---` with
`var.prop = value`, `var.key(...)` and content assignments, then removes those
overrides. Nodes created in loops or functions without a top-level binding are
refused with a clear message and their overrides stay in the file. Bake must be
exact: `run(baked program)` equals `run(program) + overrides`, and baking twice
changes nothing.

### Edit semantics in the UI

After Effects-like:

- Editing a property with no keys sets the static value.
- Editing a keyed property at the current frame sets or replaces the key at
  that frame.
- A stopwatch toggle adds the first key at the playhead or removes all keys
  (keeping the value at the playhead as a static override).
- One undo step per gesture: a drag coalesces into a single entry.

## Consecuencias

- The editor becomes an editor without ever touching the user's program;
  `bake` is the only operation that rewrites it, and it is opt-in per file.
- Provenance keys make override files fragile under edits above the call site.
  This is accepted because `.id()` exists and the UI recommends it; a stable
  content-hash identity was rejected because the same program must produce the
  same keys across runs and across the core's index remapping.
- Orphans become warnings instead of errors. `Diagnostic` gains a severity
  field; existing constructors default to `Error`, so no behaviour changes for
  programs that never load an overrides file.
- Two files must stay consistent. The editor watches both, writes the
  overrides file debounced and atomically (temp file + rename), and ignores its
  own write by comparing a content hash.
- Still deferred: override statements for blend modes, nested/animated content
  properties, and cross-file project folders. `run_with_overrides` accepts only
  the statements above; anything else is an overrides-file diagnostic.

## Addendum (2026-11-01): hybrid bake

Bake no longer only appends statements. D-0027 records value origins in the
interpreter and folds a private literal in place (a static constructor
argument or assignment, a `.key()` value and its ease) when the literal is
evaluated exactly once; everything else keeps the behaviour described here.
In-place edits shift byte-offset keys, so bake re-keys the overrides that stay
by the exact edit offsets in the same atomic write. The exactness check still
compares what the program plus the remaining overrides produce with the
expected composition.
