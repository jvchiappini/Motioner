## Contexto

The first preview window (prompt 07, D-0020) drew its chrome by hand with
`GuiBatch::rect` and `draw_text` and looked amateurish: washed-out greys, text
sitting on the bottom edge of the bars, text-only buttons and no hierarchy.
Session 012 found the root causes in the pinned engine:

1. `ferrous_core::Color::hex` stores the sRGB bytes as if they were linear and
   `to_linear_f32` is the identity, so every UI colour was encoded to sRGB a
   second time by the sRGB surface (`#2f3d4d` rendered as `#768699`).
2. `GuiBatch::draw_text` takes the top of the em box as `y` (baseline at
   `y + size`) and ignores kerning.
3. `GuiBatch::border` and `GuiBatch::shadow` pack the border width, blur and
   size into fields that `gui.wgsl` does not read, so both draw nothing useful.
4. The SVG mesh path has no anti-aliasing and overwrites per-vertex colour.
5. The engine runner owns the `UiSystem` and exposes neither resolved widget
   rects nor a re-layout hook, so `ferrous_ui_core` widgets cannot drive a
   resizable editor layout from `motioner_ui` yet.

The user asked for a top-studio editor look without changing the pinned engine
unless necessary.

## Decision

The editor chrome is an immediate-mode layer owned by `motioner_ui`, drawn on
the engine's UI batch (`DrawContext::gui`), with these parts:

- **Tokens** (`theme.rs`): the only place with colour literals, written as sRGB
  hex and linearised once with `motioner_render::srgb_to_linear` (now public;
  the single sRGB conversion in the workspace). A cool-neutral 11-step ramp,
  one accent, semantic colours, a 4 px grid, radii and an 11/12/13/15 px type
  scale. `Metrics` scales logical sizes by the DPI factor and rounds to whole
  physical pixels. Tests pin the conversion and WCAG contrast (body text
  ≥ 7:1, secondary ≥ 4.5:1).
- **Painter** (`paint.rs`): one wrapper that packs `GuiQuad`s exactly as
  `gui.wgsl` reads them (fills, borders, SDF shadows, gradients, clips,
  layers) and fills convex polygons as one-pixel scanline quads, whose edges
  the quad shader anti-aliases.
- **Text** (`text.rs`): glyphs are placed from the engine's MSDF atlas by
  Motioner, with an explicit baseline, cap-height centring, kerning, tracking,
  ellipsis and a faux medium weight (two passes half a pixel apart; the UI
  font ships one weight).
- **Icons** (`icons.rs`): a vector set on a 16-unit grid built from the
  painter's anti-aliased primitives. No bitmap assets.
- **Layout** (`layout.rs`): pure rectangles and hit testing shared by drawing
  and input, with splitters, unit-tested at several sizes and scales.
- **Panels** (`panels/`): pure drawing functions of a read-only `View`.

The engine's `UiSystem`/`ferrous_ui_core` widgets are not used for the editor
chrome yet. `motioner_ui` now also depends on `ferrous_gui` (to name
`GuiBatch`, `GuiQuad`, `TextQuad` and the quad flags) and `ferrous_font` (to
name `Font` and read its atlas); this extends the dependency list of D-0020.

## Consecuencias

- The window reaches a professional look with no engine change and no pin
  bump. Composition pixels are untouched: the golden `hello_f120.png` and the
  live-painter test stay byte-identical.
- The chrome depends on two engine details that are not formal API: the
  `GuiQuad` field meanings in `gui.wgsl` and the MSDF cell bounds
  (`[-0.3, 1.3]` em). Both are documented where they are used; an engine
  change to either must be mirrored here.
- Upstream fixes proposed for FerrousEngine (not done in this session):
  `Color::hex`/`to_linear_f32` naming or conversion, `GuiBatch::border` and
  `shadow` packing, baseline-based `draw_text` with kerning, AA for SVG
  meshes, and a screenshot hook (surface `COPY_SRC` plus
  `AppContext::request_screenshot`) so captures no longer need Win32
  `PrintWindow`.
- When GUIMaker becomes an egui-class toolkit (T-ARCH-0007), these tokens,
  icons and the painter are the natural seed for its theme and primitive
  layer; the panels would then move onto its widgets.
