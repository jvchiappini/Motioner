## Contexto

Prompt 16 approximated the HTML controller's `apply()` with transforms because
a path node's outline was static: `NodeContent::Path` owned one
`PathGeometry`, and drivers could only write transform, opacity and stroke
width. The mascot needs lids whose arc, mouth corners, body corners and bulges
are functions of properties; those values must be keyable, scrubbable and
written through to source without a second geometry implementation.

The choices were: (a) a keyable geometry channel sampled by the pure
evaluator, (b) evaluate the geometry driver at sample time, or (c) both. A
keyed channel costs one interpolation of N points per frame; a sample-time
driver costs the expression, builders, error checks and allocation per frame
and would bypass the one bake-on-build model (D-0052). The microbench
`cargo run -p motioner_rig --release --example geometry_bench` (rounded-rect
width driven from 30 to 40 over 121 frames) measures **0.5 us/frame for the
bake** versus **0.12 us/frame to sample 121 keys**; the bake runs once and the
sample runs every preview frame.

## Decision

Add a keyable geometry channel and bake geometry drivers into it.

1. `GeometryChannel` wraps a static `PathGeometry` and a sorted list of
   `GeometryKey { frame, points, ease }`. The point count and closure are the
   channel's fixed topology: `insert_key` accepts a different point count only
   as `CoreError::GeometryTopologyMismatch`, never silently. Closure, cap and
   join are shared, so keys store points only. `sample` holds outside the key
   range and interpolates positions and relative handles point-wise with the
   arriving key's ease.
2. `ContentField::Geometry` exposes the channel through the existing
   `set_content`/`add_content_keyframe` API. `ContentValue::GeometryPoints`
   carries points; the channel supplies the fixed closure/style. The DSL
   exposes `key("geometry", t, points)` and, on a rig part,
   `m.geometry(part, t, points, ease=...)`.
3. `motioner_rig::GeometryExpr` is the driver IR: `path_builder` with
   `move_to`, `line_to`, `cubic_to`, `arc_to`, `close`; whole-geometry
   `ellipse_arc`, `arc`, `rounded_rect` and `mirror`. `arc_to` implements the
   SVG endpoint-to-centre arc and emits cubic segments, so the HTML lid
   formula (`sqrt`, `sin`, `cos`, large-arc and sweep flags) is expressible.
   Commands and points are bounded; every error names the driver.
4. `Driver` gains `geometries: Vec<GeometryWrite>`. `bake` evaluates them
   after scalar writes, checks the part's base topology and puts the result in
   `PartOutput::geometry`. The DSL bake writes `ContentField::Geometry` keys,
   including a hold key before a gap, exactly like transform keys. Runtime
   evaluation therefore needs no driver support.
5. The editor verifies a geometry write-through by inspecting the compiled
   part channel (path points are content, not rig declarations) with a 1e-6
   source-round-trip tolerance, then records one undo step.

## Consecuencias

- Preview, scrub, motion blur, masks and export keep using the one evaluator;
  determinism and backwards seeking are unchanged.
- Drivers still compile once and evaluate in the bake; the runtime cost is the
  channel sample. The channel is allocation-free during sampling except for
  the returned point vector/geometry clone.
- A topology change is a refusal. Fully closed lids (`M 0 0` in the HTML) must
  be represented by degenerate points at the fixed count in E6, not by a new
  point list; this is an explicit E6 constraint, not a silent resize.
- Geometry overrides are not expressible in the override file (it has no point
  list value); source write-through and the DSL are the supported paths.
- `GeometryChannel` keys are not in `RigManifest`: points are content, so
  `Editor::apply_rig_edit` verifies them directly. Agents that need the current
  points read the document/`query` channel, not the rig manifest.
- Lattice, bones/skinning, blend shapes and constraints remain E4/E5 work.
