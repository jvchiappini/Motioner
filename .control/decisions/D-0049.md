## Contexto

Prompt 13 phases 7-10 add design analysis, render tools, media analysis and
the D-0043 agent tool runtime. Putting all of it in `motioner_app` would make
the binary the only testable surface and would let analysis reach the GPU or
the file system by accident. The boundary rules decode where each kind of
work belongs: pure measurements over the document and evaluated frames,
pixel composition over rendered frames, file and ffmpeg access, and the tool
catalogue that orchestrates them.

## Decision

### 1. Two new crates

- **`motioner_analysis`** — engine-free, file-system-free pure functions
  over `motioner_core::Document`, `motioner_eval::RenderPlan`, frames and
  decoded samples. It owns `describe_frame`, `hit_test`, `sample`,
  `code_for_node`/`node_for_code`, `motion_report`, `layout_report`,
  `legibility_report`, `check_design` and the media algorithms
  (`analyze_image`, `analyze_video`, `analyze_audio`). Text measurement and
  background sampling are injected through traits, so the crate never names
  the renderer. It also reads `motioner_dsl::ValueOrigins` for
  `code_for_node`/`node_for_code`: origins are a pure value type and the DSL
  is engine-free and file-system-free, so the mapping stays an analysis
  result rather than an editor one.
- **`motioner_tools`** — the single D-0043 catalogue and the executors that
  orchestrate the other crates: it calls `motioner_render` for images,
  `motioner_io` for files and ffmpeg, and `motioner_analysis` for exact text
  results. It depends on `motioner_ui` only through the `ProjectEditor`
  trait it defines; `motioner_app` implements that trait with `Editor`, so
  every mutating tool goes through the same write-through/checkpoint/undo
  path the window uses.

### 2. What each crate may depend on

| Crate | Allowed |
|---|---|
| `motioner_analysis` | `motioner_core`, `motioner_eval`, `motioner_dsl` (value origins only) |
| `motioner_tools` | `motioner_core`, `motioner_dsl`, `motioner_eval`, `motioner_render`, `motioner_io`, `motioner_analysis`, `serde_json` |

Neither crate may use `wgpu`, `ferrous_*`, `egui`, `eframe` or `guimaker`;
`motioner_analysis` may not use `std::fs` (checked by review and its tests).
`scripts/check_boundaries.py` encodes both rules.

### 3. Rendering stays in `motioner_render`

Overlays, filmstrips, contact sheets, zooms, diffs and the "render without
the text" background sampler are pixel work and live in `motioner_render`.
Overlays are composed in a separate pass after readback, never added to the
user's document, so exported frames cannot change.

## Consecuencias

Gana:
- Analysis is testable headless and deterministic without a GPU; the tool
  runtime can be contract-tested from a plain unit test.
- The crate graph stays acyclic and the existing boundary checker keeps
  enforcing it.

Se pierde:
- One extra hop (`ProjectEditor`) between tools and the editor.
- Two crates to keep documented in `.control/architecture`.

Pendiente:
- Media analysis may later want accelerations (SIMD, GPU); that would need
  its own ADR.
