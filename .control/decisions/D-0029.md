## Contexto

MDF v0 has no vector path. `examples/showcase.motion` draws its line art and
icons as hundreds of rectangles, and a professional piece needs a line that
draws itself, a star, an arc and an arbitrary Bezier outline. Phase 2 of the
professional-motion job adds `path(...)` plus the `polygon`, `star` and `arc`
helpers, animatable trim and dash, and real anti-aliased rendering.

Two questions had to be settled once: the authored shape of a path in MDF,
and how it becomes pixels without writing a fill tessellator.

## Decision

### Authoring model

`path(points, closed=False, fill=None, stroke="#ffffff", stroke_width=2,
cap="round", join="round", trim_start=0, trim_end=1, trim_offset=0,
dash=0, dash_offset=0)`.

`points` is a list where every element is either

- `(x, y)` — a corner, or
- `(x, y, in_dx, in_dy, out_dx, out_dy)` — a point whose incoming and
  outgoing Bezier handles are offsets **relative to the point** (`0, 0`
  means "no handle on that side").

The segment from point `i` to point `i + 1` is a cubic when the outgoing
handle of `i` or the incoming handle of `i + 1` is non-zero, and a straight
line otherwise. A closed path adds the segment from the last point back to
the first with the same rule. This is the pen model every vector tool uses,
it keeps a path a single immutable value, and it survives `query`, overrides
and bake as plain text.

Builder methods (`move_to`/`line_to`/`cubic_to`) were rejected: MDF is
expression-oriented and a node is a value, so a fluent builder would either
need mutation methods on nodes (breaking the document-as-value model and
provenance) or a second expression sub-language. A literal point list is the
smaller, more testable contract.

`polygon(sides, radius, ...)`, `star(points, inner, outer, ...)` and
`arc(radius, start, end, ...)` are ordinary MDF builtins that build the same
`PathGeometry`, so they inherit trim, dash, overrides and bake for free.
`polygon` starts at -90 degrees (a triangle points up); `star` takes the
number of spikes; `arc` takes degrees, clockwise on screen, `0` = +x, and
sweeps positively from `start` to `end` (adding 360 when `end <= start`).

### Geometry model

`PathGeometry` lives in `motioner_core::path` (points, closed, cap, join) and
is pure. It owns the single implementation of

- adaptive cubic flattening (error tolerance 0.1 local pixels, recursion
  depth cap 12), used by rendering, bounds and hit testing;
- arc-length trimming as a circular window: `s = trim_start + trim_offset`,
  length `trim_end - trim_start`, wrapping past 1; an empty window draws
  nothing and a window of length 1 or more draws the whole path;
- dashing: `dash` is the on-length in local pixels and the gap is equal to
  it, `dash_offset` shifts the pattern along the path.

Because the helpers, the DSL, the evaluator, the renderer and the editor all
use this one module, the unit tests in core are the geometry contract.

### Rendering

Fills and strokes are tessellated with `lyon_tessellation 1.0` into triangles
and submitted as `ferrous_2d::render::ShapeInstance::polygon_triangle`, which
the pinned engine already supports (the triangle SDF exists in Pure2D). Edges
shared by two triangles are marked hard (no AA) and only boundary edges are
anti-aliased, so an opaque fill has no visible seams. Strokes are tessellated
from the trimmed/dashed polylines with lyon's stroker, which honours the cap
and join style.

Tessellation is cached per node in `motioner_render`: the key is a hash of
the resolved geometry, trim, dash, stroke width and cap/join, and the cache
holds local-space triangles; the item transform is applied per frame. A
trim animation therefore re-tessellates only the frames whose value changed,
which is the steady-state cost of a draw-on.

This needs **no engine change and no pin bump**: the clone
`C:\Users\jvchi\CARPETAS\FerrousEngine` is untouched by this phase.

### Dependency: lyon_tessellation 1.0

- What: `lyon_tessellation` 1.0.23 with its `lyon_path` and `lyon_geom`
  companions.
- Why: fill tessellation (self-intersections, holes) and a correct stroker
  (joins, miter limits, caps, dashes) are weeks of work and the main source
  of rendering bugs in an NLE. Writing them ourselves is worse than trusting
  the de-facto Rust vector library.
- Licence: MIT OR Apache-2.0, compatible with the project.
- Size and supply chain: about 250 KB of source across three crates, already
  in `Cargo.lock` and in the engine (`ferrous_renderer`'s 2D shape module and
  `ferrous_svg` already depend on the same major version), so this adds no
  new crate to the build graph.
- Alternatives considered: `earcutr` (fill only, no stroker), `kurbo` (curves
  but no tessellation), a hand-written monotone tessellator (rejected for
  the reason above).

## Consecuencias

Gana el proyecto: real outline geometry with trim and dash, one geometry
implementation shared by render and editor, and the professional-motion
showcase can draw line art and icons instead of stacking rectangles.

Se pierde: `motioner_render` grows a third-party geometry dependency, and a
path item is no longer `Copy` in the plan (it references an arena entry).

Queda pendiente: canvas point editing (T-UI-0006), multi-subpath paths and
fill rules as an authoring choice, gradient fills on strokes (Phase 3), and
dash patterns beyond the 50 % duty cycle (recorded in T-RENDER-0007 notes).
