## Contexto

MDF executes once per load (spec section 2) and produces a document whose
animation is ordinary keyframes sampled by `motioner_eval`. Rive evaluates
rigs at runtime; Motioner needs rigs that are code-first, deterministic,
scrubbable, and renderable by the same pipeline as every other node, with
no second animation engine in the renderer.

Two families of rig behavior exist: **declarative** (properties, poses,
clips, state machine blends) and **procedural** (per-frame drivers such as
the mascot's eyelid trigonometry). Procedural code in the render loop
would break the "pure data to data" contract of `motioner_eval` and make
frame correctness depend on interpreter state.

## Decision

- A rig is a **component instance**: `rig(symbol, pos=..., scale=...)`
  creates a group node; every symbol part with an id becomes a real node
  reachable with `r.part("eye-L")` and iterable with `r.parts`.
- Properties are typed (`float`, `int`, `bool`, `enum`, `color`, `vec2`),
  with default, range, step, unit and optional **mirror group**
  (`r.mirror("lid", ("lid_top_L", "lid_top_R"), flip=False)`); writing or
  keying the group name fans out to both sides, per-side overrides win.
  Instances animate properties with the existing key API:
  `m.mouth_open.key(2.0, 13)`.
- Drivers are pure MDF **expression functions** registered with
  `r.driver(fn)`. `motioner_dsl` compiles the function body into a small
  `motioner_rig::Expr` IR (numbers, property reads, arithmetic,
  comparisons, `min/max/abs/sin/cos/clamp/lerp`, and a list literal of
  writes). A driver returns writes `[(part, field, value), ...]` for
  transforms, opacity, paint colour and stroke width. No node creation,
  no I/O, no statements, bounded evaluation; an unsupported construct is
  a typed compile error naming the driver.
- **Evaluation model: bake on build.** The document is derived from the
  program at every load, so rig evaluation runs once per load, over every
  composition frame, as a pure function of (rig, frame, keyed inputs);
  its output is written into the part nodes as ordinary keyframes
  (linear-interpolated per-frame samples). Preview, scrubbing, GPU
  render, motion blur, export and the golden tests therefore use the one
  existing evaluator and stay byte-identical; no renderer or eval code
  changed.
- The same rig semantics live in the new `motioner_rig` crate
  (`RigDefinition::evaluate(frame, inputs) -> FrameOutput`) and are used
  by the bake and by the headless runtime, so there is one
  implementation. `motioner_dsl` depends on `motioner_rig` only for data
  types and evaluation; `motioner_eval` does not grow a second path.
- Evaluation order per frame: property values (keys + state machine) →
  poses/clips layered values → drivers → constraints (aim, copy) →
  write to parts.
- Bounds: drivers may write at most 64 writes per part per frame, at most
  4096 writes per frame, and evaluation is capped at the composition
  frame count.

## Consecuencias

Gana:
- Deterministic, frame-exact rigs with zero changes to the evaluator and
  renderer; scrubbing backwards is trivially correct because the output
  is keys.
- Rigs work in exports, goldens, motion blur, masks and effects with no
  special cases.

Se pierde:
- The document carries one key per animated channel per frame (bounded
  by duration x channels); a 15 s 60 fps mascot demo is a few tens of
  thousands of keys, measured in the report.
- Drivers cannot edit path geometry in v0 (path points are not a keyable
  content channel); deformers and path-editing drivers are backlogged for
  the native-deformer phase.
- Interactive rigs at runtime need the headless runtime replaying the
  baked curve or re-evaluating `motioner_rig` (Phase 10).

Pendiente:
- True runtime evaluation (no bake) when the editor preview needs to
  change rig inputs without recompiling the program; the rig crate is
  the seam.
