## Contexto

A document optimized for editing (stable IDs, arbitrary hierarchy,
undo history, rich metadata) is a poor structure for rendering, which
wants flat, cache-friendly, GPU-ready data. Reusing the editing model as
the render model couples the UI and the renderer and makes caching and
determinism harder.

## Decision

Keep the editable document and the render runtime separate. The
evaluator compiles a document version plus a frame into an explicit
render plan: flat render items, resolved transforms, effect parameters,
pass hints and resource requirements.

- The document owns identity, hierarchy, time and authoring state.
- The runtime owns flat arrays, caches and GPU handles derived from
  document revisions.
- Engine entities and GPU resources are runtime artifacts, never
  persisted as truth.
- Incremental caches are keyed by revision hashes and may be dropped at
  any time without losing data.

## Consecuencias

Gains:
- Editing model and render model can evolve independently.
- Flat render plans are fast, testable without a UI and easy to cache.
- Engine can be replaced at the adapter boundary.

Costs:
- A compile step and revision tracking must be maintained.
- Duplication between document and runtime representations.
- Every new feature needs mapping in both models.

Pending:
- Define the render plan schema and its stability guarantees.
- Define dirty tracking and revision hashing granularity.
- Decide whether some runtime structures are persisted as optional cache
  for faster startup.
