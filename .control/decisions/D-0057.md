## Contexto

D-0036 makes write-through the default: an edit becomes a byte-range code
edit, the editor re-runs the program and checks the result exactly. Rig
declarations are different from node properties: `m.pose`, `m.clip`,
`m.state` and a property key do not write a core property at the moment they
run; they change the rig's own model, which the compiler bakes into node keys
afterwards. Value origins therefore do not contain them, and an
`OverrideSet` cannot express them.

Prompt 16b E2 needs three things at once: an exact source edit, one undo step
and a way to reject an edit that changes the wrong thing. It also has to
answer what happens when the declaration lives inside a used `.motion`
module (`m = rigs.build(...)` where `build` declares the pose).

Options considered:

1. Add rig declarations to `ValueOrigins` and extend `EditCommand`. That
   couples the core command surface to rigs and still needs a second planner.
2. Rewrite the module file when the declaration is there. The editor writes
   one program atomically; a second file introduces a cross-file transaction,
   watcher loops and a second undo target.
3. Plan against the calls in the file that binds the rig root and refuse
   module declarations with a reason (chosen).

## Decision

- `motioner_dsl::rig_edit` defines `RigEdit` (set/key/unkey, pose apply/
  save/delete, clip key/remove/length/play, state/transition/input edits and
  mirror sides) plus `plan_rig_edit`.
- The planner finds the rig root's `NodeOrigin`, takes the assignment that
  binds it in the open program (`m = rig(...)` or `m = module.build(...)`) and
  walks only that block. Calls on the bound variable and on clip handles
  assigned in the same block are the edit anchors; calls inside function
  definitions are not.
- Property edits write a `.set(...)`/`.key(...)` call. A mirror group writes
  the group name (`m.lid.set(0.6)`) so the runtime flips the right side; a
  single side writes the concrete property (`m.lt_R.key(...)`).
- The manifest (D-0056, schema v2) gains each property's authored keys. After
  applying the edit, the editor compiles the candidate and compares the new
  manifest with `apply_to_manifest`, which mirrors runtime order (pose tracks
  and plays stay in authoring order) and refreshes derived machine inputs and
  events. It also checks that every node outside the rig subtree is unchanged.
  A mismatch is a refusal, never a guess.
- A declaration that lies in a used `.motion` module is refused with a reason
  naming the module boundary. `motioner` does not edit a second file behind
  the open program's back. A later module editor can lift this without
  changing the tool contract.
- Every successful edit is one `CodeEdit`, one atomic program write, one undo
  entry and `Strategy::RigEdit` in reports and traces.

## Consecuencias

Gana:

- Agents and the future rig panel share one edit path with drags: plan,
  verify, write, undo.
- Module declarations cannot be corrupted silently; the refusal says why.
- Property keys and declarations are visible in the manifest, so the editor
  can verify a rig edit without re-deriving the rig runtime.

Se pierde:

- Editing a pose, clip or state declared in a helper module needs a manual
  code edit until module write-through exists.
- The manifest duplicates the runtime channel keys (D-0056 already accepted
  the duplication for properties). The mapping stays in one place in
  `motioner_dsl`.

Pendiente:

- The rig panel (T-RIG-0009) builds its view-models on this sink.
- Module write-through remains a separate feature.
