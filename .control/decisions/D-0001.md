## Contexto

Motioner needs real-time 2D and 3D rendering and must support custom
engine work. The user already owns FerrousEngine, a wgpu-based Rust
engine with ECS, assets, a render graph, 2D and 3D crates, fonts and a
UI toolkit. Building a renderer from scratch would duplicate that work
and delay the product.

## Decision

Use FerrousEngine as the rendering and application foundation. Pin a
specific engine revision, wrap it behind an adapter crate
(`motioner_render`), and treat engine modifications as small,
upstreamable patches recorded in ADRs. The engine is not vendored into
this repository yet; it will be added after the design gate.

The pinning mechanism (git submodule versus a fork branch referenced by
path or git revision) is finalized when the engine is added. The
constraint is reproducibility: every build must use the same recorded
revision.

## Consecuencias

Gains:
- Reuse a custom engine designed for exactly this use case.
- One rendering stack, with 2D, 3D, PBR, fonts and a render graph.
- Engine improvements benefit both the engine and Motioner.

Costs:
- The engine API is young and will change; pinning and adaptation are
  mandatory.
- Deep engine changes can become a second product to maintain.
- The editor's release cadence is coupled to the engine revision.

Pending:
- Choose submodule versus fork branch and document the update process.
- Define which engine crates Motioner depends on.
- Establish an upstream contribution convention for patches.
