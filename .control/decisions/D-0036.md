## Contexto

D-0022 made the editor an editor "without ever touching the user's program":
every UI gesture becomes an entry in `<name>.overrides.motion`, and only an
explicit `motioner bake` folds entries back into the code. D-0027 made bake
hybrid: the interpreter records a `ValueOrigin` for every property write, and
bake replaces a literal in place when it is private to one node.

That keeps the program pure, but it splits the truth in two files and the
program the user (or a model) reads is not the program that renders. It also
throws away the most valuable thing Motioner can produce: **clean MDF code
written by people and by the editor, paired with the action that produced
it.**

The product strategy confirmed by the user on 2026-11-03 depends on that
code:

1. Generate a large, high-quality MDF corpus with a frontier model (Claude
   Fable 5) plus the edits people make in the editor.
2. Distil it into an **extremely small model specialised in motion design**
   that writes MDF. A small model that is excellent at one language is cheap
   to serve, can run locally later (D-0012 left local models open) and is a
   product that can be sold (D-0015: AI credits).
3. Ship an **agent panel inside the app**: a harness that talks with the
   user and calls tools like a chat with Claude, using the same command
   surface as the UI (D-0024).

All three need the program to be the single source of truth and the code
the editor writes to look like code a good motion designer would write.

## Decision

### 1. Write-through is the default

Every editing command (D-0024) that changes the document is resolved into a
**code edit**: a set of byte-range replacements on the program text, planned
by `motioner_dsl` from the recorded origins. The overrides file is written
only when no exact code edit exists (section 4).

- During a gesture (drag, scrub of a number field) the document is patched in
  memory exactly as today; the preview never waits for a re-run.
- At gesture end the planner produces one code edit, the editor applies it
  atomically (temp file + rename), re-runs the program and checks that the
  result equals the expected document (the D-0027 exactness check, identities
  compared by position). One gesture is one write and one undo step.
- Undo/redo store the inverse text patch plus editor state; undoing a gesture
  restores the exact previous bytes.
- External edits (code panel, VS Code, an agent) are picked up by a file
  watcher; the editor re-runs and keeps selection by identity when it can.
- `motioner edit` and the live control endpoint use the same path. A
  `--overrides` flag (and an editor setting) keeps the D-0022 behaviour for
  read-only programs and for comparison tests.

### 2. Strategy ladder

For each resolved change the planner tries, in order, and takes the first
that is exact:

1. **Private literal** (D-0027): replace the literal in place.
2. **Loop specialisation**: the value came from a literal or expression in a
   loop body that feeds several nodes. The interpreter records the loop
   stack of the write (loop span, loop variable, iteration index and value,
   body span). The planner inserts a guarded statement **inside the loop
   body, right after the last statement that writes that node**:

   ```python
   for i in range(5):
       c = circle(40, fill="#ffffff")
       c.pos = (200 + i * 120, 540)
       if i == 3:
           c.fill = "#ff4d4d"
   ```

   Rules:
   - The guard uses the loop variable: `if i == 3:`. Nested loops combine
     guards (`if row == 2 and col == 5:`).
   - An existing guard for the same node and the same condition is extended,
     not duplicated. Two iterations with the same value merge into
     `if i in (1, 3):`; when every iteration ends with the same value, the
     shared literal is edited instead (the UI asks "this one / all" only when
     both are exact; default "this one").
   - A node created inline without a binding gets one (`c = circle(...)`,
     fresh readable name) so the guard can reference it.
   - `for _ in ...` is renamed to an unused readable name; a loop over
     non-integer values guards on the value when it is a unique literal
     (`if name == "b":`) and otherwise is rewritten to
     `for i, x in enumerate(xs):` (the language gains what it lacks, in the
     spec).
   - Keys follow the same rule (`if i == 3: c.key("opacity", 1.0, 0.5)`).
   - Deleting one loop instance uses `if i == 3: continue` at the top of the
     body when that iteration creates only that node; otherwise it is a
     fallback.
3. **Call-site specialisation**: the node comes from a function called from
   several places. If the function already takes a parameter for the value,
   pass it at that call site. If the function returns the node, assign after
   the call (`b = badge(...)` / `b.fill = ...`). Otherwise **promote the
   literal to a keyword parameter** whose default is the old literal
   (`def badge(x, fill="#ffffff")`) and pass the new value at that call site;
   other call sites are unchanged by construction.
4. **Local assignment**: a computed value on a bound node becomes an
   assignment placed right after the node's last write in its block, never in
   a trailing generated block.
5. **Fallback**: an override entry with a reason (D-0022), shown in the UI
   with a "convert to code" action once the program allows it.

The ladder is deterministic: the same program, document and command always
produce the same edit.

### 3. Structural edits write code

- Adding a layer inserts a constructor statement with a readable variable
  name from its kind and role (`title`, `circle`, `circle_2`), after the
  selected node or at the end of the composition body.
- Deleting removes the creation statement and every statement that only
  touches that variable; anything shared falls back.
- Duplicate, rename (`node.name`), reorder, keys (add, move, remove, ease),
  stopwatch and `visible` are code. `locked`, selection, expansion and panel
  layout are editor state and live in the project's editor state file, not in
  the program.
- Inserted code follows the surrounding indentation and the canonical style
  of `motioner fmt`; the user's comments, order and formatting outside the
  edited range are never touched.

### 4. Overrides stay as a fallback

The overrides file keeps its format, loading, orphan warnings and `bake`.
New edits only reach it when the ladder ends in fallback or the user chose
overrides mode. The editor shows the count of pending overrides and why each
is there.

### 5. Canonical style

`motioner fmt` (idempotent, comment-preserving) and `motioner lint` (idioms:
named bindings for edited nodes, no dead guards, no magic duplicates) define
the style that generated code and the training corpus follow. The editor
never reformats a file on its own; formatting is an explicit command.

### 6. Edit traces

Every committed edit can produce a trace record: program before (hash and
text), the D-0024 command text, the strategy used, the code edit, the program
after and the frame. Agent sessions produce the same records with the
conversation and tool calls around them, so UI edits, agent edits and
synthetic generation share one format.

- Traces are local, stored under the project's `traces/` folder.
- Recording our own corpora (synthetic generation, internal dogfooding) is on
  in development builds. For end users it is **off by default**; sharing is
  explicit opt-in per project with a clear explanation, never automatic
  (D-0012: nothing is uploaded without the user).
- The format is a documented export for training tools (one record per line,
  stable field names, versioned), not a document format; D-0005 still governs
  project files.

### 7. Agent harness (future, same surface)

The in-app agent panel is a harness: a conversation, a provider abstraction
(D-0012), and tools that are exactly the D-0024 commands plus code tools
(read program, apply code edit, run, query, render still). Its edits go
through write-through, so they are code, undoable, reviewable as a diff and
recorded as traces. `motioner tools --schema` publishes the tool list so the
harness, external agents and the training data use one schema.

## Consecuencias

Gana:
- One source of truth: the program renders what the user sees, and the code a
  person or a model reads is the real one.
- Every UI action is a labelled example of "intent → idiomatic MDF edit",
  which is exactly what a small motion-design model needs.
- Loop and function edits stay readable (`if i == 3:` and parameters instead
  of opaque provenance keys), and keys stop shifting because fewer overrides
  exist.
- The agent panel and external agents need no private path.

Se pierde:
- The editor now writes the user's program; a planner bug corrupts code. The
  exactness re-run, atomic writes and byte-exact undo are mandatory, and the
  planner falls back instead of guessing.
- Each committed gesture costs one interpreter run; budgets are measured on
  the biggest example and recorded.
- More language surface (`enumerate`, `in` tuples, guards) to specify and
  test.

Supersedes in part:
- D-0022 "the editor never touches the user's program" and "bake is the only
  operation that rewrites it": write-through is now the default; overrides
  and bake remain as fallback and migration tools.
- INITIATIVE-0014 non-goal "model training or fine-tuning" applies to the app
  only: training runs in a separate pipeline fed by traces and synthetic
  corpora, outside the editor.
