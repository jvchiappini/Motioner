## Contexto

Motioner renders with FerrousEngine, a custom wgpu-based engine that
lives in its own repository and is not published on crates.io. The engine
repository also carries large assets (skybox, models, brain, web models
and test batches) that Motioner does not need to build, test or render.

Motioner needs a reproducible, reviewable way to consume the engine
without copying its source and without depending on a developer's local
checkout. Only `motioner_render` reads the engine crates; the rest of the
workspace must stay independent of graphics code. The dependency boundary
checker previously had no DSL rule and banned all graphics prefixes for
every crate.

## Decision

Pin FerrousEngine as a git submodule at `engine/ferrous`; `shallow` is
declared at `.gitmodules:4`. The current pin is
`02e6d4873379e3f7b92406bd5c63d0ad1c80bdee`, dated 2026-10-31.

The checkout excludes the large asset directories through sparse patterns
documented in `engine/README.md:20-29`. The root workspace excludes
`engine/` at `Cargo.toml:14`. The engine path dependencies are declared
at `Cargo.toml:31-35` and consumed only by
`crates/motioner_render/Cargo.toml:13-15`.

Dependency rules are enforced as data in
`scripts/check_boundaries.py:26-64`: `motioner_dsl` may not depend on
evaluation, rendering, I/O, UI or application crates, and only
`motioner_render` may use the `wgpu` and `ferrous` prefixes. `egui`,
`eframe` and `guimaker` stay forbidden for every crate.

Engine changes are made as small upstreamable patches on a branch in the
FerrousEngine repository. After they land, the pin is bumped in Motioner
with a new ADR and the documented procedure in `engine/README.md:48-70`.

## Alternativas consideradas

- Vendoring the engine source into `engine/ferrous`: rejected because it
  duplicates the upstream history, hides upstream changes and makes
  patch review harder.
- A git dependency in Cargo: rejected because the engine is not published
  and its repository layout and assets are not designed for cargo fetch;
  it also gives less control over shallow and sparse checkout.
- An external checkout outside the repository: rejected because it is
  machine-specific, not reproducible in CI and easy to point at the wrong
  commit.
- A deep full submodule: rejected because it clones large unused assets
  and slows every fresh clone and CI run.

## Consecuencias

Gains:
- Reproducible engine builds from a single pinned commit.
- Small clone and CI footprint thanks to the shallow and sparse checkout.
- Upstream improvements remain reviewable as small patches.
- Graphics dependencies stay confined to `motioner_render`.

Costs:
- Cloning requires `git submodule update --init --depth 1` and the sparse
  patterns; in Git Bash, `MSYS_NO_PATHCONV=1` is needed.
- Every engine bump is an explicit, documented step with a new ADR.
- CI must check out submodules, so it is slightly slower to start.

Pending:
- Sparse patterns may need to change if new engine directories become
  required.
- Upstream features such as 2D text may later reduce local adapter code.
