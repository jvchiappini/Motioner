# D-0030 - Gradient paint model and the Pure2D gradient pass

## Context

Phase 3 adds `linear_gradient(start, end, stops)` and
`radial_gradient(center, radius, stops)` to `fill`/`stroke` of rects,
circles, paths and text, with animatable stop colours and positions built on
the D-0028 content-channel machinery. The renderer must reproduce the
authored sRGB stops exactly and must not band on large, low-contrast ramps.

The pinned Pure2D pass (`shape_2d.wgsl`) draws every instance with **one
straight linear RGBA colour**; `ShapeGpu` is exactly 64 bytes with every flag
bit assigned, and the sprite, text and grid pipelines have no per-pixel
gradient either. `ShapeInstance::polygon_triangle` has one colour for the
whole triangle, so "colour per vertex over a lyon mesh" is not available
without a shader change. Drawing one thin strip per band was rejected:
adjacent strips re-run the shape AA, which double-blends the silhouette and
cannot dither.

Conclusion: per-pixel gradients with exact stops and dithering cannot be
implemented on the pinned engine. The engine gets a new **Engine Part A**
(implemented in the clone, the reviewer bumps the pin) and the Motioner side
stops at `RenderError::Unsupported { feature: Gradient }` until then, with
the whole authoring model, editor and tests already in place.

## Decision

### Authoring model

```
fill = linear_gradient(start=(x, y), end=(x, y),
                       stops=[(0.0, "#ff5a6e"), (1.0, "#7c5cff")])
fill = radial_gradient(center=(x, y), radius=240,
                       stops=[(0.0, "#ffffff"), (0.6, "#7c5cff"), (1.0, "#16121f")])
```

- `Gradient` holds a static `GradientKind` (`Linear { start, end }` or
  `Radial { center, radius }`) and 2..=16 stops. Each stop is
  `{ offset: Animatable<f64>, color: Animatable<Color> }`, so offsets and
  colours key, override, bake and appear in the timeline with the same
  stopwatch as any other content channel (D-0028).
- Gradient geometry is authored in the node's local space, like path points.
  It is **not** animatable: moving/rotating/scaling the node moves the
  gradient. (Animating start/end is a later backlog item; it would be two
  vector channels.)
- Offsets are clamped to `0..=1`; the list is sampled sorted by offset, so a
  user can key an offset past its neighbour without reordering the rows.
  Two stops at the same offset produce a hard edge.
- Interpolation is linear-light sRGB per channel, alpha included, exactly
  like `Color::lerp` (D-0028). A pixel whose gradient parameter is exactly a
  stop offset returns the authored sRGB byte.
- Paint carries a solid colour *and* an optional gradient per fill/stroke
  (`fill_gradient`, `stroke_gradient`). Setting a solid colour clears that
  gradient; setting a gradient keeps the last solid colour as the fallback
  used by previews that cannot draw gradients. Rendering prefers the
  gradient.
- Text uses the same model for its **fill** (`color=` accepts a gradient).
  Text has no stroke in MDF v0, so stroke stops are rejected for text.
- `ContentField` gains `FillStopOffset(u8)`, `FillStopColor(u8)`,
  `StrokeStopOffset(u8)` and `StrokeStopColor(u8)`; their names are
  `fill_stop0_offset`, `fill_stop0_color`, ... and `from_name` parses them.
  Field names are dynamic, so `ContentField::name` returns `String` and the
  core errors that carry a field name store `String`.

### Render plan

Plan items stay `Copy`: `ItemShape` carries `ResolvedPaint` made of
`ResolvedFill::{Solid(Color), Gradient(usize)}` indices into a new
`RenderPlan::gradients` arena. The evaluator resolves stops per frame
(offset sampled, colour sampled, sorted) and pushes one `ResolvedGradient`
per gradient used by the frame.

Motioner returns `RenderError::Unsupported { feature: Feature::Gradient }`
when an item uses a gradient and the engine has not reported support. The
error carries the node id and feature, is reachable through `motioner
render`/`still`, and is asserted by a render test. Nothing silently falls
back to the solid colour.

### Engine Part A (clone, uncommitted)

The clone adds gradients to the Pure2D shape pass (and the text pass for
glyph fill):

- `ShapeGpu` gains `gradient: u32` (0 = solid, otherwise a slot in a
  per-frame storage buffer).
- The shape bind group gains a read-only storage buffer of `vec4<f32>`:
  a gradient header `(kind, first_stop, stop_count, 0)` and params
  `(start.xy, end.xy)` or `(center.xy, radius, 0)`, followed by two vec4 per
  stop `(linear rgba)` and `(offset, 0, 0, 0)`. Gradients are in **world**
  space, which every shape path already carries, so one descriptor works for
  rects, circles, paths and triangles.
- The fragment shader evaluates the ramp in linear light, converts the
  result to sRGB, adds an 8x8 ordered (Bayer) dither of at most one code
  value, and converts back to linear for the sRGB attachment. The dither
  amplitude fades to zero at each stop so the authored bytes are exact.
- Text: the MSDF glyph fragment gets the same gradient lookup, using the
  glyph's world position and the node's resolved opacity.
- Engine tests cover packing, the storage layout, and a headless render of a
  linear and a radial ramp (exact stop bytes and a max-neighbour-step
  assertion).

## Alternatives considered

- **Strip/band meshes with one colour per instance**: no dithering, AA
  double-blend on silhouettes, thousands of instances. Rejected.
- **CPU rasterisation into a sprite texture**: cannot mask arbitrary shapes
  and cannot touch glyph interiors; 8 MB per node per frame. Rejected.
- **Baking the gradient into a texture array sampled by the shape shader**:
  adds a texture binding and sampler filtering blur; exact stop bytes are
  harder than evaluating the stops directly. Rejected.
- **Animating the whole gradient as one value** (one key holds all stops):
  simpler, but the prompt asks for animatable stop colours and positions,
  and per-stop rows are what the editor needs. Rejected.

## Consequences

- Until the pin moves, gradients author, key, edit and query correctly but
  the renderer refuses them with a typed error, so a gradient layer cannot
  silently look wrong. Phase goldens are generated against the clone and are
  skipped while the pinned engine reports no support; the next session
  regenerates/verifies them after the bump.
- `RenderError` gains `Unsupported { feature, node }`; the app prints it
  instead of panicking.
- The storage buffer is uploaded once per frame; a document with no
  gradients allocates nothing beyond the empty buffer and the shader branch
  is a single bit test.

## Implementation notes (2026-11-01)

- Engine Part A landed in the FerrousEngine clone, uncommitted: `ShapeGpu`
  grew to 68 bytes with a `gradient: u32`, `ShapeInstance::with_gradient`
  selects a table entry, `Uniform2d` carries `gradients: [[f32;4]; 512]` and
  `shape_2d.wgsl` evaluates the ramp in linear light with an 8x8 Bayer dither
  that fades at the stops. `Renderer2d::set_gradient_table` and
  `Renderer::set_2d_gradient_table` upload it. Tests:
  `crates/ferrous_renderer/tests/pure2d_gradients.rs`.
- Motioner gains the `engine-gradients` feature (off by default). It builds
  the table, transforms each gradient by its item's world transform and calls
  `with_gradient`; without the feature, any gradient plan returns
  `RenderError::Unsupported { feature: Gradient, node }`.
- The text pass is **not** part of Engine Part A yet: the glyph pipeline has
  no gradient index and `TextInstance` was left untouched. Text gradients are
  therefore refused with the same `Unsupported` error even with the feature;
  the authoring/editor side is complete.
- Radial gradients under a non-uniform scale use the x-axis scale (the shader
  draws a circle). Documented in the renderer README.
- Goldens `gradients_f30.png` / `gradients_f105.png` were rendered with the
  clone and the feature. `golden_gradients.rs` compares them when the
  renderer supports gradients and skips cleanly on the pinned engine.
## Amendment (2026-11-01, Phase 4 start)

- The engine pin now carries the gradient pass (857b9df), so the
  `engine-gradients` feature is deleted: the gradient table upload and the
  per-instance reference are unconditional.
- The engine side gained a general encoder, `ferrous_2d::render::GradientTable2d`
  (`Gradient2d`, `GradientKind2d`, `GradientStop2d`), documented in
  `crates/ferrous_2d/docs/gradients.md`; Motioner keeps only the
  plan-to-world adapter in `motioner_render::gradients`.
- Text gradients are implemented in the engine (`TextInstance::with_gradient`
  and `Renderer::draw_text_2d_with_gradient`, shared camera/gradient WGSL in
  `pure2d_common.wgsl`). Until the pin is bumped, Motioner guards them with the
  temporary `engine-text-gradient` feature and returns
  `Unsupported { feature: Gradient }` by default.
- `golden_gradients.rs` now includes a gradient-filled headline; the two
  goldens were regenerated against the clone and are skipped on the pin until
  the bump.
## Amendment (2026-11-02, Phase 5 start)

- The temporary `engine-text-gradient` feature is **deleted**: the text pass
  calls `draw_text_with_gradient` unconditionally. The pin (e9fb90d) carries
  `TextInstance::with_gradient`, so no `cfg` and no `Unsupported` branch for
  text gradients remain in `motioner_render`.
- `golden_gradients.rs` no longer skips: any render error, including
  `Unsupported`, fails the test, and both stills are compared on every run.
- `motioner_render` has no temporary engine features left; its only feature is
  `live` (the window adapter).
