## Contexto

Motioner is a command-line renderer today (`motioner render|still|info`).
The user needs to see and use the composition: open an `.motion` file in a
window, play it, scrub it, inspect its scene tree and see it reload when the
file changes on disk.

D-0004 chose the engine-native UI stack (Ferrous UI and GUIMaker, no egui) and
planned the viewport as an engine render into a texture that the UI displays.
Two facts changed the plan since then:

1. GUIMaker is a standalone designer binary that imports `ferrous_app`, which
   no longer exists in the pinned engine; it cannot be a dependency yet.
2. The pinned engine's Pure2D path can draw a composition directly into the
   window's 2D pass, before the UI pass. A viewport texture is unnecessary for
   a first live preview and would add a second device/format path.

The engine's `FerrousApp` already provides the one window, one device and one
event loop that D-0004 requires.

## Decision

Add a new library crate, `motioner_ui`, that implements the first editor
window directly on the pinned engine.

Allowed dependencies (the boundary script enforces the list):

- `ferrous_engine` — `App`, `AppMode`, `FerrousApp`, `AppContext`,
  `DrawContext`, `Color`.
- `ferrous_renderer` — the `Renderer` type that `LivePainter` paints into.
- `ferrous_gui`, `ferrous_ui_core`, `ferrous_2d` — UI widgets and 2D types if
  the window needs them.
- `wgpu`, `glam`, `winit` — only through the engine's re-exports where
  possible; `winit` only if a raw window event handler is implemented.
- `motioner_core`, `motioner_dsl`, `motioner_eval`, `motioner_render`.
- It must not depend on `motioner_io`, `motioner_ai`, `motioner_app` or
  `motioner_testkit`.

The first implementation actually depends on `ferrous_engine`,
`ferrous_renderer`, `motioner_core`, `motioner_dsl`, `motioner_eval` and
`motioner_render`. It does not link `ferrous_gui`, `ferrous_ui_core`,
`ferrous_2d`, `wgpu`, `glam` or `winit` directly: the engine facade and
`motioner_render` expose everything the window uses.

`motioner_ui` uses the engine's UI *rendering* path (`DrawContext::gui`, a
`GuiBatch`) for its immediate panels, and the engine's Pure2D pass for the
composition. GUIMaker integration is deferred to T-ARCH-0007.

What this corrects in D-0004:

- The GUIMaker dependency: `motioner_ui` depends on the engine UI crates, not
  on GUIMaker, while GUIMaker cannot build against the current engine.
- "Viewport rendered into a texture and displayed by the UI": the first window
  draws the composition directly in the window's Pure2D pass, letterboxed by a
  `ViewFit` transform, and the engine draws the UI pass on top. No offscreen
  viewport texture is created.

What stays from D-0004:

- No egui and no second toolkit.
- One device and one event loop.
- Panels, outline, transport and timeline live in `motioner_ui`; generic
  widgets are still contributed upstream when they are reusable.

## Alternativas consideradas

- Wait for GUIMaker to build against the current engine: rejected; it blocks a
  visible, usable window on an unstarted task.
- Use egui: rejected by D-0004 (and it would add a second GPU stack).
- Render the composition into an offscreen texture and blit it: rejected for
  the first window because the Pure2D pass already draws straight to the
  window and the UI pass composites on top.

## Consecuencias

Gains:

- A real window this milestone: open, play, scrub, outline and hot reload.
- The engine's one-device/one-loop rule is preserved.
- No dependency churn when GUIMaker becomes buildable: the widgets are a later
  upgrade, not a prerequisite.

Costs:

- The first window's chrome is custom-drawn; it does not yet use retained
  widgets such as split panes or tree views.
- `motioner_render` gains a `live` feature whose `LivePainter` names an engine
  type. That is the documented exception; the default build stays engine-free
  at the public API.

Pending:

- T-ARCH-0007 decides GUIMaker's architecture and the widget contribution
  boundary.
- Replacing the custom chrome with engine widgets or GUIMaker-generated code
  is a follow-up after the toolkit builds.
