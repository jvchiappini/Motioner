## Contexto

Prompt 16 stored the result of a rig as baked keys, and the runtime rig
(properties, poses, clips, machine) lived only inside the compiler's
`Scene`. The editor, `query` and agents therefore could not list what a rig
offers without reading the program, and the future rig panel would have had
to re-derive it. The manifest has to survive the compile, belong to the
document it describes, and be deterministic.

Options considered:

1. Keep the runtime `motioner_rig::Rig` in the document. It would make
   `motioner_core` depend on `motioner_rig` (which already depends on core
   and eval), a cycle; and the runtime model includes evaluation state that
   is not document data.
2. Store an opaque JSON string. No typed access, no stable schema version
   and no compile-time guarantee that the fields exist.
3. Define typed manifest records in `motioner_core`, build them in the DSL
   at the end of the bake, and keep them on `Document` (chosen).

## Decision

- `motioner_core::rig_manifest` defines the versioned, typed records
  (`RigManifest`, `RigInstanceManifest`, properties, parts, poses, clips,
  plays, layers, aims and the machine). `RIG_MANIFEST_VERSION` is `1`.
- `Document` carries one `RigManifest` with `rig_manifest()` and
  `set_rig_manifest()`. It is descriptive data only: evaluation still comes
  from the baked keys, and a changed manifest never invalidates the node
  tree or the evaluator cache.
- The DSL builds the manifest after `bake_rigs`, from the same `RigEntry`
  list that was just baked, in authoring order. Missing indices are skipped
  instead of panicking.
- `motioner query <file> --rig <instance>` (and `query rig <file> <instance>`)
  prints `{"version":1,"rigs":[...]}` with fixed field order. The shape is
  the `rig_manifest` result schema in `motioner tools --schema`.
- The manifest is not serialised into MDF: the program is still the source
  of truth and the manifest is rebuilt on every compile.

## Consecuencias

Gana:

- Editors and agents read one typed description instead of parsing code or
  re-deriving runtime state.
- The version field makes a schema change explicit; the reader can reject or
  migrate an older manifest.
- `motioner_core` stays dependency-free: the records are plain data and the
  JSON writer lives in `motioner_ui`.

Se pierde:

- The manifest duplicates part of the runtime types. The mapping is in one
  place in `motioner_dsl` and a DSL test pins it against the mascot.
- A large document pays one allocation per rig instance on compile; the
  measurement from E0 (50 mascots) will show it.

Pendiente:

- E2 adds rig edit tools that read and write through this manifest; E7 adds
  the panel view-models. `RigManifest` is not yet exposed to the wasm player
  (T-RIG-0015).
