## Contexto

Motioner is AI-first (`PROJECT.md`): an LLM must be able to do everything a
person can do in the editor. After prompt 08 the only way to drive the editor
was `scripts/ui_drive.ps1`, which posted mouse clicks at pixel coordinates and
used SendKeys with window focus: fragile, Windows-only and blind to errors.

The editor's actions were also split: `input::Action` (transport, selection,
undo) and `edit::EditCommand` (override entries), with the resolution between
a gesture and an override (keyed or static, which ease, which value) spread
over a 2900-line `app.rs` and duplicated between the inspector, the gizmo and
the timeline. A second, agent-only implementation would have drifted.

## Decision

### One command layer

`motioner_ui::Command` is the single typed vocabulary of editor actions: 45
variants covering transport, selection, view toggles, panel sizes and scroll,
every editing action of the inspector, timeline, canvas and layers panel,
orphans, undo/redo and bake. Each variant has a stable text name
(`CommandKind::name`), a signature, an example and a canonical text form that
parses back to the same value.

`motioner_ui::Editor` is the window-free editor state (session, transport,
selection, expanded rows, view state, undo) and the **only executor**:
`Editor::execute(&Command)`. The window maps every press, drag, wheel turn,
shortcut and field commit to a `Command`; `input::Action` and `input::Effect`
are deleted. A drag opens an editor gesture: intermediate commands resolve
against the state at the press and coalesce into one undo step, so a drag
equals the single command of its end state.

`EditCommand` stays as the internal, resolved form (one override change);
commands resolve into it and `edit::apply` applies it.

### Text syntax: MDF calls

Commands are MDF function calls parsed by `motioner_dsl::parse` (no new
grammar): `edit("title", "pos.x", 900)`, `key("title", "opacity", 1.5, 0.5,
ease="quad_out")`. Arguments mirror the overrides file of D-0022: identities
and property names are strings, times are seconds, values are numbers,
`(x, y)` pairs or strings. `frame(N)` names an exact frame where seconds
would round (`move_key(..., frame(60))`).

### Surfaces

1. Headless, no window, CI-friendly:
   - `motioner query <file> [--frame N] [--node ID]` prints the scene.
   - `motioner edit <file> [--frame N] [--dry-run] <command>...` runs
     commands through `Editor::execute` and writes the overrides file
     atomically, all or nothing; it prints the commands' results and the
     removed and added override lines.
   - `motioner bake` and `motioner info --json` go through the same code.
2. Live: `motioner preview <file> --control [--control-file F]` opens a TCP
   endpoint on `127.0.0.1` with an OS-chosen port and a random 128-bit
   token, written with the pid to `<temp>/motioner/control.txt` (or `F`) and
   removed on exit. A background thread accepts connections and forwards each
   request through a channel that `update` drains without blocking a frame.
   `motioner ctl [--endpoint F] <request>...` sends any command plus the
   queries `state()`, `query(node=None)` and `screenshot(path)` (the in-app
   capture hook of D-0023).

### Output format: JSON for tool output

`query`, `state`, `edit` results and every `ctl` reply are single-line JSON
objects with a fixed field order (nodes in outline order, channels in display
order), written by a small hand-made writer (`motioner_ui::Json`). This is
**tool output, not the document format**: D-0005 (MDF is the document, no
JSON/RON documents) is untouched, nothing in Motioner parses JSON, and no
dependency was added. JSON was chosen over an MDF-like text because every
LLM and shell tool reads it reliably and the output is never fed back as a
program. Errors are `{"ok":false,"error":{"kind":"...","message":"..."}}`
with stable kinds (`parse`, `unknown_command`, `bad_argument`,
`no_document`, `unknown_node`, `unknown_property`, `no_selection`, `no_key`,
`bad_value`, `io`, `refused`).

### Parity is tested

- Every `CommandKind` has a unique name, an example whose text round-trips,
  and a signature in `--help` (exhaustive `match`es: a new variant fails to
  compile until it has a name, a signature and an example).
- `agent_parity.rs` runs the prompt 08 manual session only through
  `motioner edit` and `motioner bake` and compares the overrides text and the
  document with the same edits written through `edit::apply`; it also checks
  every example reaches the executor from the command line and parses to the
  same command for `ctl`.
- `live_control.rs` starts `preview --control`, drives it with `ctl`, takes a
  screenshot and checks state and undo (skips without a GPU).

## Consecuencias

Gains:
- An agent can open, inspect, select, scrub, play, edit any property,
  add/move/delete keys, change eases, hide/lock/rename, undo/redo, delete
  orphans, bake and take screenshots without coordinates or focus.
- One implementation per action; `app.rs` (2913 lines) became `app/` (window
  glue) plus the `editor` module (state and rules) that tests can drive.
- Bugs found by the refactor: replacing a key reset its ease to linear; K
  toggled keys off instead of adding; a whole-vector gizmo key next to axis
  keys was lost on reload (the file sorts `pos` before `pos.x`). Vector keys
  are now always written per axis.

Costs and limits:
- Headless `edit` keeps no undo history between invocations (each run is one
  transaction); the live editor keeps the normal history.
- The endpoint trusts any local process that can read the endpoint file
  (same user). It never listens on other interfaces.
- `quit()` and view commands are accepted but have no lasting effect in
  headless `edit`.
- Canvas zoom does not exist yet, so there is no zoom command.
